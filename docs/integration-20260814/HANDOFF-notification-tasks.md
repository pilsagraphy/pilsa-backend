# 알림(toast) 기능 — 담당자 과제

> 작성 2026-08-16 · PM 배정 문서
>
> **이 문서는 "이렇게 만들어라"가 아니라 "여기까지 되어 있으니, 나머지는 설계해서 가져와라"입니다.**
> 엔드포인트 경로·요청/응답 형태를 여기서 정해주지 않습니다. 본인이 설계하고 PM 확인을 받은 뒤 구현하세요.

---

## 1. 지금 어디까지 되어 있나 (읽고 시작할 것)

알림의 **발행(알림이 생기는 것)과 웹 푸시 전달**은 완성되어 동작 중입니다. 아래 파일을 직접 열어 확인하세요.

| 무엇 | 파일 |
|---|---|
| 알림 발행 로직 | `src/main/java/com/back/mypage/notification/service/NotificationService.java` |
| 알림 종류 정의 | `src/main/java/com/back/mypage/notification/dto/NotificationType.java` |
| 웹 푸시 발송 | `src/main/java/com/back/mypage/notification/service/NotificationPushService.java` |
| 수신 기기 등록부 | `.../controller/NotificationDeviceController.java`, `.../mapper/NotificationDeviceMapper.java` |
| 알림 저장 쿼리 | `src/main/resources/mapper/mypage/notification/NotificationMapper.xml` |
| 발행을 호출하는 쪽 | `src/main/java/com/back/board/service/BoardServiceImpl.java` 에서 `NotificationService` 를 찾아볼 것 |
| 테이블 | `notifications`, `notification_devices` (DDL 적용 완료 — 스키마는 DB에서 직접 확인) |
| 웹 푸시 배경 지식 | `docs/integration-20260814/PUSH-NOTIFICATION-GUIDE.md` |
| 프론트 연동 규약 | `docs/integration-20260814/HANDOFF-notification.md` |

**즉, 알림 데이터는 지금도 계속 쌓이고 있습니다. 다만 회원이 그것을 볼 방법이 없습니다.**

## 2. 과제

### 과제 A — 알림함 화면이 동작하게 만들기

기획상 헤더의 **종 아이콘**을 누르면 알림함이 열리고, 회원은 자기 알림을 확인·정리할 수 있어야 합니다.
화면에서 필요한 동작은 대략 이렇습니다.

- 종 아이콘에 **안 읽은 알림이 몇 개인지** 표시된다
- 알림함을 열면 **내 알림이 최신순으로** 보인다 (안 읽은 것만 보기도 필요)
- 알림을 **하나 읽음 처리**할 수 있다
- **전부 읽음 처리**할 수 있다
- 알림을 **지울** 수 있다

여기까지가 요구사항입니다. **어떤 API가 몇 개 필요한지, 경로와 메서드는 무엇인지,
요청·응답을 어떤 모양으로 할지는 본인이 설계하세요.**

설계할 때 스스로 답해야 하는 질문들(예시이며, 이게 전부는 아닙니다):

- 목록이 많아지면 어떻게 할 것인가? 한 번에 다 내려도 되는가?
- 남의 알림을 읽음/삭제 처리하는 요청이 오면 어떻게 막을 것인가?
- 이미 읽은 알림을 또 읽음 처리하면 어떻게 되어야 하는가?
- 알림을 지운다는 것은 이 프로젝트에서 어떤 의미인가? (§3 규칙 참고)
- 목록을 부를 때마다 미읽음 수를 따로 또 불러야 하는가?

### 과제 B — 발행되지 않는 알림 종류 붙이기

`NotificationType` enum을 열어보면 정의된 종류와, `NotificationService` 에서 **실제로 발행되는 종류의 수가 다릅니다.**

- 몇 종이 정의되어 있고 몇 종이 실제로 발행되는지 직접 확인하세요.
- 발행되지 않는 것들은 **각각 어느 도메인의 어느 시점에 발행되어야 하는지** 판단해서 연결하세요.
  (힌트: 발행 메서드는 이미 다 만들어져 있습니다. 호출하는 쪽이 없을 뿐입니다.)
- 연결 후 **알림이 가면 안 되는 경우**가 없는지 반드시 검토하세요. 이미 그런 방어 로직이 하나 들어 있으니 찾아보고, 같은 기준을 적용하세요.

### 과제 C — 스스로 판단해서 제안하기

위 A·B를 하면서 **"이것도 있어야 하지 않나?"** 싶은 것을 찾아 PM에게 제안하세요.
알림함을 실제로 써본다고 상상하면 빠진 게 보입니다. 제안은 근거와 함께 가져오세요.

## 3. 반드시 지킬 프로젝트 규칙

`CLAUDE.md` 를 먼저 정독하세요. 아래는 이 과제에서 특히 자주 틀리는 부분입니다.

- **소프트삭제가 대전제** — 이 프로젝트에 물리 삭제는 없습니다. 이유까지 이해하고 적용하세요.
- **현재 사용자 판별은 `AuthUtils`** — 직접 SecurityContext를 뒤지거나 파라미터로 userId를 받지 마세요.
  (요청 본문·쿼리로 userId를 받는 설계는 그 자체로 보안 결함입니다.)
- **MyBatis 파라미터 2개 이상이면 `@Param` 필수**
- **`boolean isXxx` 금지, `Boolean isXxx` 사용** — 이유는 CLAUDE.md에 적혀 있습니다.
- **에러 응답은 항상 `{"message": ...}` JSON**
- URL은 `/api/user/**` 아래. 알림 API는 `toast` 네임스페이스를 씁니다.
  ("구독"이라는 단어는 캘린더 구독과 혼동되므로 알림 쪽에서 쓰지 않습니다.)
- **스웨거 문서화 필수** — 기존 컨트롤러(`NotificationDeviceController` 등)의 `@Operation` 작성 수준을 보고 맞추세요.

## 4. 완료 기준

1. 설계안을 **먼저** PM에게 확인받는다 (API 목록 + 각각의 요청/응답 + 실패 케이스).
2. 구현 후 `./gradlew compileJava` 통과 + 실제 기동해서 호출까지 확인한다.
3. 확정된 API를 **명세 정본(`api_endpoints` 테이블)에 반영**한다.
   기존 행들을 보고 같은 형식으로 작성할 것. (planned → active 로 바꾸는 것도 포함)
4. 본인 브랜치에서 작업 후 PR. 커밋 메시지는 기존 커밋 로그 형식을 따를 것.
